# 纯词列表导入 · 设计

一个文件里只有词、没有编码，导入时按目标方案现场出码，落进用户词库。

状态：阶段 A、B 均已实现。
- 阶段 A（wind-setting）：`8bd945b`
- 阶段 B（WindInput）：`EngineManager::encode_words` / `generate_words_pinyin` +
  `dict.encodeWords`，实测 1000 词批量 1.86ms vs 逐个 618ms（**332x**，见 §4.3）

## 1. 目标与非目标

**目标**：`.txt` 一行一个词 → 选目标方案 → 自动出码 → 合并/替换进该方案的用户词库。

**非目标**：
- 不做一行多词的切分（`你好 世界` 视作一个词条还是两个，无法从文件本身判定，交给用户预先整理）
- 不做多音字消歧的人工干预（一个词取一个码，取 core 现有出码入口的结果）
- 不涉及短语、临时词库、词频、候选调整——纯词列表只进用户词库

## 2. 已确认的决策

| 项 | 决定 |
|---|---|
| 格式识别 | 严格自动识别（整体 sanity check + 逐行过滤），**并在对话框里显示格式且允许用户手动指定** |
| 权重 | 对话框里让用户填，给默认值 |
| 出码性能 | **分批请求**（每批 ~1000 词），不做全量单次调用 |
| 出码预览 | **不做**。选文件只做客户端解析报词数；出码在点「导入」时发生一次 |
| 实施顺序 | 先出设计与 UI；core 改动待确认后开工 |

## 3. 架构：出码为什么放在客户端分批

最初的设想是「core 在 `dict.import` 内部识别纯词列表并顺手出码」。**分批这个约束把它否掉了**，
结果反而更好——core 的改动面从三个 crate 收缩到一个 RPC。

### 3.1 否掉 core 内部一次做完的理由

- `rpc::call_core` 有 5 秒硬超时（`rpc.rs` `CALL_TIMEOUT`）。两万词的同步出码 + 入库几乎必然撞线，
  而超时后客户端放弃、core 那边还在跑，状态无从判断。
- `EngineManager::encode_word`（`manager.rs:714`）每次调用都 `read_schema`（**读并解析方案文件**）
  再取 `single_char_full_codes`。循环两万次就是两万次文件解析。这不是常数因子问题，是量级问题。
- 预览要报「多少条出得了码」，import 时若再算一遍，等于全部翻倍。

### 3.2 采纳的分层

```
纯词列表解析        wind-setting（客户端）    按行切分，无需 core；选完文件即时出结果
分批出码            dict.encodeWords（新）    每批 ~1000 词，一次 RPC 一批；点导入才发生
落库                dict.import（现有）       客户端把出好码的行拼成 TSV 提交
```

**关键收益：`wind-store` 与 `import_formats` 完全不用改。** 出码后的行是标准的
`code<TAB>text<TAB>weight`，走现有 TSV 导入通道即可——那条路的解析、去重、merge/replace
语义、报告格式全部现成。core 侧只新增一个批量出码 RPC。

拼音方案出的是**带空格的音节码**（`ni hao`）。这条路同样安全：`parse_words_tsv` 的
`normalize_code` 保留单空格（注释明确写着「rime 词库里的空格是词库作者标注的音节真值」），
落库时 `wdict` 再按有无空格拆成 flat+boundary。无需特殊处理。

### 3.3 与既有机制的衔接

- **切换「导入到」目标方案**：无需任何处理。出码在点「导入」时才发生，那之前不存在
  依赖方案的中间结果——这正是不做出码预览换来的最大简化（原设计要在这里作废缓存并重出码）。
  只有说明文案里的方案名要跟着变，而它已经是响应式的。
- **自动重定向**：纯词列表没有来源引擎标记，`sourceEngine` 为空 ——
  现有 redirect 逻辑要求该字段非空，天然不触发，不会把用户莫名其妙地弹到别的方案。
- **混输目标**：混输不收 userWords，现有的「一条也不会导入 + 请改选目标方案」提示直接复用。

## 4. 接口契约（core 新增）

### 4.1 `dict.encodeWords`

```jsonc
// 入参
{ "schemaId": "wubi86", "texts": ["中国", "计算机", "𰻞𰻞面"] }

// 返回：codes 与 texts 严格同序等长；出不了码的位置回空串（不是省略、不是 null）
{ "codes": ["khgo", "yttw", ""] }
```

同序等长是契约的要害：客户端靠下标把码配回词，长度对不上就无法安全配对。
出不了码用空串而非跳过，正是为了保住这个不变式。

出码规则与 `dict.encode` 完全一致（拼音走 `generate_word_pinyin`，其余走 `encode_word`），
实现上把 `web_dict_encode` 里那段引擎分派抽成私有方法给两处共用，避免两条出码口径漂移。

### 4.2 `EngineManager::encode_words`

```rust
/// 批量出码：spec 与单字码表在循环外准备一次。
/// 单次 encode_word 每调一次就 read_schema 一次，循环里用会退化成 N 次方案文件解析。
pub fn encode_words(&self, schema_id: &str, words: &[&str]) -> Vec<String>
```

这是 4.1 能跑起来的前提，不是可选的优化项。

### 4.3 实测：批量 vs 逐个

`cargo test -p wind-engine --test engine_manager encode_words_batch_is_faster -- --ignored --nocapture`

```
1000 词：批量 1.8593ms / 逐个 617.9142ms → 332.3x
```

按这个斜率，逐个调用下 10000 词约需 6.2 秒——**单次 RPC 必撞 5 秒超时**，
即最初设想的「core 在 import 内部一次做完」根本跑不通，不是慢一点的问题。
批量后同样 10000 词分 10 批共约 19ms。

该对照测试带 `#[ignore]`（性能数字随机器波动，不适合当门禁），但保留下来是有用的：
若日后有人把 `encode_words` 改回内部循环调 `encode_word`，倍率会立刻塌回 1x。

## 5. wind-setting 侧流程

```
选文件（瞬时，不发 RPC）
  └→ 客户端解析（§6）→ 词列表 + skipped + duplicates
       └→ 回显「识别为 纯词列表 · 3180 个词（跳过 3 行 · 去重 12）」

点「合并/替换导入」
  └→ 分批出码：每 ENCODE_BATCH=1000 调一次 dict.encodeWords
       └→ 剔除空码行，计入 unencodable
            └→ 拼 TSV（code\ttext\t<用户填的权重>）
                 └→ dict.import（sections=["userWords"]）
                      └→ toast：已导入 N 条（M 条出不了码已跳过）
```

出码只发生在导入这一步，全程一遍。选文件与切目标方案都不触发 RPC，
因此不存在需要作废的中间状态。

### 5.1 分批与界面响应

`rpc::call_core` 是同步阻塞的，分批循环会冻结 UI 线程直到全部批次返回。

- **阶段一（本次）**：同步分批。常见词表 2000–5000 行 = 2–5 批，冻结 1–2 秒，可接受。
  批大小 1000 使单批稳在超时预算内，规模再大也只是慢，不会失败。
- **阶段二（按需）**：若实测上万行体验不可接受，升级为后台线程 + channel 回 UI 报进度。
  这条路有现成先例：升级下载就是 `app.channel::<UpdateMsg>` + `AppState::set_update_tx`
  （channel 只能在 App 构建期注册，见 `main.rs` 的注释）。

先做阶段一，不预先背上异步的复杂度。

## 6. 格式识别

### 6.1 判据

现有 `detect_dict_format` 的 `Unknown` 分支正是纯词列表的落点。收编它会带来一个代价：
**任何不含制表符的文本都会被当成词表**，用户误选 `.md`／日志／代码文件时，
原本明确的「无法识别的词库格式」会退化成一屏垃圾预览。

故采用严格判据，两道关：

1. **整体 sanity check**：非空非注释行中，"看着像词"的比例 ≥ 90%，否则仍判 Unknown 报错。
   像词 = 纯 CJK + 长度 ≤ 12 字 + 无内部空白。
2. **逐行过滤**：通过第一关后，不像词的行计入 `skipped` 并在预览里报数。

识别放在客户端（`wind-setting`），因为 §3.2 里解析本就在客户端。core 的
`detect_dict_format` 不动——它那条路只处理带编码的文件。

### 6.2 格式行（UI）

自动识别不可能永远对，所以格式要**可见且可改**：

```
格式    [ 自动识别 → 纯词列表        ▾ ]
```

下拉选项：`自动识别` / `WindDict 词库` / `Rime 词库` / `TSV 文本` / `纯词列表（自动出码）`。
默认「自动识别」，选完文件后在同一行回显识别结果。用户手动指定即覆盖自动结果并重新预览。

这同时解决了两件事：严格判据误伤时用户能强制指定；平时也让用户看得见"系统把这个文件当成什么"。

## 7. UI 变更

导入对话框在现有结构上增两行，都只在格式为「纯词列表」时出现：

```
┌ 导入 · 五笔86 · 码表 ─────────────────────────┐
│ 从 WindDict / Rime / TSV / 纯词列表导入        │
│ [选择文件…]  my-words.txt                      │
│ 导入到  [ 五笔86 · 码表            ▾ ]         │
│ 格式    [ 自动识别        ▾ ] 识别为：纯词列表 │← 新
│ 权重    [ 1200 ]                               │← 新（仅纯词列表）
│ ☑用户词库                                      │
│ ─ 提示区（固定视口）─                          │
│ 识别为 纯词列表 · 3180 个词（跳过 3 行·去重 12）│
│ 编码将按「五笔86 · 码表」现场生成，出不了码的   │
│ 词会被跳过。                                    │
│                  [关闭][替换导入][合并导入]     │
└────────────────────────────────────────────────┘
```

- 「权重」仅纯词列表显示——其余格式的权重来自文件本身，给输入框会造成"能覆盖"的误导。
- 需明确一句「编码按目标方案现场生成」：这是纯词列表独有的性质，也是"换方案得重来"的由来。
- 文件选择器的 filter 已含 `txt`，不用改。

### 7.1 格式下拉只给两项

阶段 A 的选项是 `自动识别` 与 `纯词列表（自动出码）`，**不给 WindDict / Rime / TSV**。

理由：强制指定这三种需要 core 的 `dict.previewImport` / `dict.import` 接受 format 参数
（它们现在一律自动识别），阶段 A 给了也不生效——列一个点了没反应的选项比不列更糟。
而纯词列表的强制指定是纯客户端能力，立即可用，也正是严格判据误伤时的救济通道。

真需要覆盖那三种时再随 core 一起加。

## 8. 边界与错误处理

| 情况 | 处理 |
|---|---|
| 出不了码（生僻字／方案未配拆字） | 跳过，**导入结果 toast 报数量**。不阻止其余词导入 |
| 全部出不了码 | 不发 `dict.import`，直接报错「无一可出码，请确认目标方案」。<br>注意这只能在导入时发现——不做预览就换不来"提前禁用按钮" |
| 文件内重复词 | 客户端解析时去重，保留首次出现 |
| 编码与库内已有词冲突 | 交给现有 merge/replace 语义，不特殊处理 |
| 目标为混输 | 复用现有「混输不收用户词库」提示 |
| 空文件／全是注释 | 判 Unknown，报「文件不含可导入的词条」 |
| `codes` 与 `texts` 长度不符 | 视为 core 契约违例，整体报错而非按下标硬配 |
